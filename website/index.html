Product

Five moving parts, one window

Everything an agent needs to be useful more than once: an identity, a room to work in, a memory that fits in a budget, a CLI to run on, and a real terminal when you want to drive it yourself.

An agent is a profile, not a prompt

Name, role, standing instructions, model, effort, permission mode, tool allow and deny lists, extra directories, context budget. Every field lands on a real flag when the turn is spawned — nothing is decorative.

  • Import a whole team from a folder of .md files
  • Per-agent memory lanes beyond the channel's own
  • A persona edit starts a fresh session instead of silently rotting

Rooms decide who answers

A channel has a topic, a roster and a lane. Post once and every agent on the roster replies; write @reviewer and only they do. What is said in a room is remembered in that room's lane.

  • Chat, standup, review and terminal kinds
  • Broadcast to the room or mention one agent
  • Same transcript on desktop and phone, live

Memory that fits in a budget

Every turn ends with a FACTS: block. Those become high-weight chunks; the reply itself becomes a low-weight one. Before the next turn they are ranked, compressed and truncated to the project's token budget — so a long project does not mean a long bill.

  • Lanes keep unrelated work out of each other's context
  • Pinned chunks survive compaction
  • The pack rides on the message, so it survives a resume

Capabilities

Put a whole team on one repository

The parts that make several agents usable at once, rather than several chat windows you have to keep in your head.

Fan-out turns

One message reaches every agent in the room, or exactly the one you named. Each answer is its own process, its own budget, its own permissions.

Context lanes

Memory is partitioned by lane, so the infra thread never bleeds into the auth thread. An agent may read past its own lane only when you say so.

The architect

Describe the outcome; a master agent proposes the team, the channels and the briefs, then applies them in one step. Edit anything it guessed wrong.

Plugin catalogue

Browse, install and enable Claude Code plugins and marketplaces from inside the app. The same ones a plain claude session sees.

Phone as a remote

No CLI on a phone. It writes a queued run instead, and the desktop that does have one claims it and executes. Same transcript, same data.

Keys that stay put

API keys live in one file on the machine that spawns the processes — never in the database, never in argv, never on a teammate's laptop.

Keys are handed over, not stored around

One JSON file on the machine that runs the agents, 0600 where the OS allows it. Nothing is written to the database: a key synced through a shared project would be readable by everyone in it, and a binary path is meaningless on anyone else's machine.

A variable whose key is blank is left unset rather than set empty — so a CLI you signed into interactively keeps using its own credentials instead of being handed nothing.

Context engine

Turns that stay cheap on turn two hundred

The constraint that shapes the whole app: a team of agents on a long project will re-read the same history forever unless something stops them. Two rules do the stopping.

01

Answers are compressed by contract

Every persona carries an output contract: drop articles and filler, keep every path, identifier and number exact, never touch code or error strings. Short answers cost less to produce and less to remember. 

OUTPUT CONTRACT (strict):
- Fragments allowed. Terms, paths, numbers exact.
- Code blocks and errors: verbatim.
- Max 12 lines unless emitting code.
- End with FACTS: 1-3 durable facts.
02

Only the durable half is kept warm

The reply becomes low-weight memory. The FACTS: block becomes high-weight memory. Next turn, chunks are ranked by weight and recency, compressed, and cut to the budget — the pack stays the same size whether the project is a day or a year old. 

pack(lanes, budget) -> 1,024 tokens
  kept    12 chunks   (weight × recency)
  dropped 41 chunks
  rides on the message, so --resume keeps it

0keys or secrets written to the database

Architecture

Three pieces, one source of truth

The desktop app spawns processes. PocketBase holds the data. The frontend owns every write — which is why a phone with no CLI sees exactly what the desktop sees.

Desktop

Tauri + Rust

Spawns the CLI, streams stdout back to the webview as it arrives, compresses and budgets context, and runs a real PTY when you want the TUI. It writes nothing to the database.

  • Headless turns and interactive sessions
  • Cancellable runs, per-run registry
  • Windows console never flashes
Data

PocketBase

Projects, agents, channels, messages, context chunks, goals, sessions and runs. Realtime subscriptions push every change to every device, with a slow poll behind them for when a stream quietly stalls.

  • Nine collections, migrations in the repo
  • Runs as a queue for devices without a CLI
  • Docker image pinned and non-root
Client

React + MUI

One codebase for desktop and phone. Light and dark, a frameless window with its own chrome, and a settings panel that puts project data and machine-local keys side by side without mixing them up.

  • Optimistic writes, no round-trip to see your own message
  • Streaming drafts flushed on a timer, not per token
  • Theme stamped before first paint

Principles

Opinions this thing is built on

An agent that cannot be configured is a demo. Every field in the agent editor lands on a real flag.

Agent model

Context is the bill. Compress by contract, keep the durable half, and cap what a single turn may spend.

Context engine

Secrets belong on the machine that spends them, in the environment of the process that needs them.

Key vault

The vendor is a setting. Nothing about a team of agents should depend on who ships the CLI.
